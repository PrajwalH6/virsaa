### Retest

- **Viewports:** Headless Chromium loaded the updated build at 360×800, 390×844, 412×915, 768×1024, 1366×768 and 1920×1080. The public page and authenticated fixture dashboard fit each viewport. No uncaught JavaScript page errors were observed. The mock workflow deliberately injected one connection reset and a failed login. Public asset requests canceled by navigation were tracked separately from CSP violations.
- **Mocked browser workflows:** Reservation validation, normalized submission, lost-response retry, pending/confirmed tracking, deferred tracking cancellation, contact form, sign-in/out, ordinary and super-admin gating, outsider denial, password reset, approval/rejection/cancellation, search/date/status filtering, pagination, timed refresh, staff actions, and WhatsApp compose/copy.
- **Automated suite:** 15 passed, zero failed, and one hosted Cloud suite skipped. This included the Chromium keyboard/404 test, mocked Edge authorization and invitation recovery, and embedded PostgreSQL tests for both schema paths.
- **Production build:** `npm run build` succeeded on Node 24.22.3. It emitted both the main app and `dist/404.html`.
- **Hosted limits:** The tests used fixture records and a local server that applied the configured headers. No current hosted integration checks were performed. Production SMTP, Formspree delivery, PostgREST rate-limit behavior, Edge CORS/Auth, real WhatsApp handoff, and Vercel route/header delivery still need release verification.

### Release checklist for the existing project

1. Complete the Windows `pg_dump` backup and verify its archive before proceeding. Record the current Vercel and Edge Function revisions and agree on a data-preserving rollback. The earlier production inventory showed four reservation references and one super admin. Compare the current baseline again before and after the release.
2. Once approved, run [the incremental migration](supabase/migrations/20261128134951_cafe_readiness.sql) in the existing Supabase SQL Editor. It is wrapped in a transaction. It adds booking support and rate counters without deleting reservations or changing the established super-admin role. Do not run the fresh-install schema against this project.
3. Update the existing `manage-staff` Edge Function and verify `SITE_URL=https://vrisaa.vercel.app` and the two existing Auth redirect URLs. Coordinate this with the frontend release because the migration revokes legacy frontend access paths. The approved Docker-free Edge deployment command and secret instructions are in [BUG_FIX_REPORT.md](BUG_FIX_REPORT.md).
4. After approval, push the reviewed branch, update the GitHub About URL, and publish using the existing Vercel project and production branch. Confirm Node 24.x, the public Supabase environment variables, [the production domain](https://vrisaa.vercel.app/), unknown-route HTTP 404 and the response headers. Complete hosted smoke checks with separately approved test data.
5. If the release fails, pause production writes and compare the symptoms against the preflight snapshot. Restore the previous frontend and Edge revision only alongside a compatible database interface. Use a reviewed, targeted schema rollback or forward fix that retains bookings added since the backup. A full restore can overwrite newer data and requires separate approval.

## Original audit baseline

### Summary

The local updated frontend passed a browser-driven reservation flow against mocked services. A customer submitted an in-memory request, recovered the same reference after a simulated lost response, an admin approved it, and the customer tracked the confirmed status. The browser produced both WhatsApp compose URLs. The production Supabase inventory supplied earlier shows that the updated frontend cannot run that flow against the existing production schema.

The café currently responds at [vrisaa.vercel.app](https://vrisaa.vercel.app/). That site serves a different, older bundle. The repository's public homepage setting points to `virsaa.vercel.app`, which returned Vercel's `DEPLOYMENT_NOT_FOUND`. [GitHub repository metadata](https://api.github.com/repos/PrajwalH6/virsaa)

No production form was submitted, no real customer or staff credentials were used, and no email or WhatsApp message was sent. Live browser requests were restricted to read-only HTTP methods. All local service writes were routed to an in-memory fixture. Application code, database settings, GitHub, and deployed services were left untouched. Screenshots contain public content or synthetic fixture data.

## Pipeline and security notes

- **Mock pipeline:** A synthetic booking was created in memory, returned the same reference after retry, appeared in the admin view, changed from pending to confirmed, and was shown as confirmed to the customer. Separate mocked actions covered cancellation and rejection. WhatsApp URLs were intercepted before any message could be sent.
- **Local database and Edge checks:** Twelve targeted Node, Edge mock and embedded PostgreSQL tests passed. The SQL tests covered fresh and incremental schemas, booking retry, tracking, role and RLS checks, historical rows, status-change rules, and pagination beyond 200 entries. They do not verify hosted PostgREST or GoTrue behavior.
- **Live database comparison:** The earlier read-only inventory showed four reservations, one existing super admin, an existing staff role column, and an anonymous UUID-only tracking RPC. Those counts reflect the supplied inventory. This audit did not re-query production rows. Applying the database migration alone would revoke the older frontend pathways before the new frontend is live. Publishing the updated frontend alone would point it at RPCs missing from production. The backup must be verified before an approved cutover.
- **Browser technical checks:** Public route scans produced no uncaught JavaScript exceptions. Some image and font requests were aborted when navigating away. The mock run deliberately blocked external assets and injected a failed login response and a booking connection reset. Those events are test conditions rather than evidence of a deployed outage. No live Supabase write, token validation, or Edge error rate was measured.
- **Build and configuration:** The production build succeeded and emitted `dist/404.html` in build output. Local browser tests used a dummy Supabase project URL and key. A separate configuration check confirmed that the repository environment and the live bundle point to the same Supabase project and public key. No server-key markers were detected in that bundle. Verified live HTTP statuses were 200 for `/`, `/admin`, `/admin/setup`, and `/admin/reset-password`. HTTPS and HSTS were present. The sampled live homepage response had no Content Security Policy header. The absence is a defense-in-depth observation, not evidence of script injection.
- **Remaining unverified:** Real Supabase transactions and concurrent requests through PostgREST, real authenticated admin sessions, deployed Edge authorization/CORS, Formspree delivery, live invitation and recovery email, actual WhatsApp app handling, native mobile keyboard/pickers, and HTTP 404 on the updated Vercel deployment.
